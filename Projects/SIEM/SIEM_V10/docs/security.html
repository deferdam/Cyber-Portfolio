Security documentation

The core shift: in local mode the app trusts its single operator and the local machine. In server mode it is reachable by several users over a network, it holds accesses, and it becomes a target. Every implicit trust must become an explicit, server-enforced control. This page is the threat model for that move and the v10 hardening plan.

Posture by version

  • v9 (local): file analysis stays on the analyst machine. Risky binary parsers (pcap, evtx) never touch a server.
  • v10 (server): read-only. The app may read, never mutate the host. Ships only after the hardening below.
  • v11: active response (ban IPs, set files read-only to quarantine ransomware), gated behind v10 hardening.

1. Authentication and sessions

  • No auth exists today; anyone reaching the port has full access. Need login with hashed passwords (argon2 or bcrypt), never plaintext.
  • Secure cookies (HttpOnly, Secure, SameSite), protection against session fixation and hijacking, sensible expiry.
  • CSRF protection on state-changing endpoints once cookies are used.
  • Rate limiting and lockout against login brute force.

2. Authorization (the most important)

  • Server-side scoping: "My tickets" currently filters in the browser. In multi this must be enforced on the server by assignee equals the authenticated user. A client filter is not a control.
  • IDOR: ticket reads and updates must check ownership or role. Guessable ids without a check leak or mutate other users' tickets.
  • Vertical escalation: manager and CISO actions (template editing) must be checked on the server, not merely hidden in the UI.

3. Privilege / mode integrity (the privilege glitch)

The local versus server mode must be set by a trusted server-side config, never by a client header or query param. If the server can be tricked into local mode, it exposes the local code paths: no auth, file browser, binary parsers. That is a full bypass. Confining pcap and evtx to local is what makes this containable.

4. Input validation and injection

  • Path traversal: the local file browser must resolve real paths, reject .. and symlink escapes, and stay confined to a root. Removing it from the server removes this risk there.
  • Stored XSS: the SPA builds HTML by concatenation with raw values (notes, host, command_line). In multi, one user's note could inject script that runs in another's session. Escape all such values on render before multi ships.
  • Template injection: note-template substitution is a plain string replace, never an eval-like render.
  • Parser abuse: oversized records, deeply nested JSON, archive bombs. Apply size and depth limits, stream, isolate per record.
  • Binary parsers (pcap, evtx): memory-safety and RCE risk in third-party libraries. Confined to local, never on the server.

5. Data at rest and in transit

  • At rest: tickets are plaintext JSONL. Encrypt at rest so raw disk access reveals nothing. Key custody options to evaluate: a physical USB key holding the key, or a VeraCrypt-style container. Tension: security versus fast operator access.
  • In transit: plain HTTP over a LAN allows sniffing and MITM, including credential capture. Require TLS. (Clipboard copy also needs a secure context, so it is blocked on plain http over an IP.)
  • Secrets: OAuth tokens for mail must be encrypted, never in plaintext config, never logged.
  • The app now binds to 127.0.0.1 by default. It must never be exposed to a network without the controls above.

6. Concurrency and integrity

  • The ticket store appends to a JSONL file; concurrent writers corrupt it. Multi needs a real datastore or strict locking.
  • Two operators on one ticket cause last-write-wins overwrites. Need optimistic concurrency (a version field) or locking.
  • Note drafts live in browser localStorage, per machine; they do not follow a user across devices in multi. Acceptable, but documented.

7. Availability and accountability

  • Unauthenticated heavy endpoints (run-stream, ingestion) allow resource exhaustion. Authenticate, rate limit, cap file sizes and connection counts.
  • Append-only, tamper-evident audit log of who changed status or disposition and when. It also feeds the "inform others" goal and future auto-triage.

8. Admin panel and access control (v10)

  • Dedicated admin tab to create and manage users, with a dashboard of all people, their roles and accesses.
  • Two admins maximum, both with full access.
  • Four-eyes control: sensitive actions (create user, create admin, change role or access) require approval by the second admin. The approver must differ from the requester, enforced on the server, and every request and decision is audit-logged.

Open risk to resolve. Two-admins-max is a single point of failure: if one is unavailable, the approval queue deadlocks. A break-glass recovery path is required. Dual control should apply to sensitive actions only; on routine actions it is too heavy.

9. Machine learning auto-triage safety (v10)

  • Confidentiality: model artifact and training data behind admin auth; the model can memorize sensitive ticket content, so protect it.
  • Anti-poisoning (the hard problem): do not auto-retrain on raw labels. Track label provenance per user, rate-limit one user's influence, review training data, monitor label-distribution drift, keep a human in the loop.
  • Anti-saturation: rate-limit inference, cap input size.
  • Access: none without the admin role; reached from the admin panel.

10. Endpoint exposure (v10)

Naming sensitive routes unpredictably and hiding URLs is security through obscurity: a secondary layer only, never a primary control. URLs leak (logs, history, referrers). A static 6-character code shared among admins is a weak sole gate (shared secret, leakage, brute force without strict rate limiting). Prefer per-user MFA (TOTP). Keep an obscure path or a code only as defense in depth on top of real authentication and server-side authorization, never instead of them.

11. AI input safety (v10)

Mails and ticket content fed to any model are untrusted text. Never interpret or execute them; pass them through a validating parser. Parsing alone does not stop prompt injection, so also separate instructions from data in the prompt and filter the output.

12. Mail integration (v10)

  • Read professional mailboxes only, never personal, even when a user connects both. Minimize OAuth scope (read-only, specific labels).
  • A machine aggregating all employees' mailboxes is a large centralized risk. Verify encryption end to end and access control before considering it.

13. Deployment hygiene

No Flask debug mode in production (the Werkzeug console is RCE). Manage the secret key. Lock down CORS. No default credentials.

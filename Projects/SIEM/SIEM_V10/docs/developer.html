Developer documentation

Read this top to bottom and you can navigate and extend the code. The system is a one-direction pipeline: each stage consumes the previous output and never reaches backward. Adding a format means adding a reader; nothing downstream changes.

1. The pipeline

raw source
  -> reader        (format specific, src/ingest)
  -> normalizer    (raw dict -> Event, owns event_type and field mapping)
  -> detection     (OS-gated Sigma + heuristics, dedup, process-context attach)
  -> correlator    (signals -> alerts)
  -> reporter      (writes normalized_events / signals / alerts to out/)
  -> SOAR          (signal -> playbook -> Ticket, writes tickets.jsonl)
  -> web UI        (reads out/, renders dashboard, tickets, signals)

The detection stage is where the most subtle logic lives: it runs the modules for the current OS, deduplicates and merges signals, then attaches process context (ancestors, children, and the triggering process itself) from the process tree, after the merge.

3. Data model

Event (normalized)

Produced by the normalizer. Key fields: event_id, event_time_utc, event_type (for example process, file, auth), host.hostname, and process (a ProcessRef with name, pid, ppid, image_path, command_line). The original raw record is kept under raw.

Signal

A frozen dataclass emitted by detection. Carries signal_type, score, severity, mitre_technique, explanation, recommended_actions, evidence_event_ids, and the process context: process_ancestors, process_children, process_self. Because it is frozen, enrich it with dataclasses.replace, never by assignment.

Ticket

Not frozen. Built by Ticket.from_signal. Adds workflow fields: status, assignee, notes, disposition (the analyst verdict, feeds future auto-triage), and the same process context fields propagated from the signal.

4. Adding an ingestion format (the reader contract)

A reader is a function path -> iterator of raw dicts. Each dict uses the keys the normalizer already understands, so the rest of the pipeline is untouched. Register it in _READERS.

Minimum keys to emit per record:

KeyMeaning
event_idstable id for the record
timestampISO 8601 string
sourceshort tag (sysmon_like, auditd, snort, ...)
hosthostname
event_typeprocess for process events (required for the tree), else a tag
pid, ppidintegers for process events (required for the tree)
image_path or process_namethe binary; the tree derives the node image from it
command_linefull command; most detection matches on this

The lesson that cost real debugging time. Two independent traps leave the process tree empty even when pids look fine:

  • The record is not typed process (for sysmon-like input the normalizer defaults missing event_type to file), so the tree never registers a node.
  • The record is typed process and has pid and ppid, but the binary name is not extracted (auditd EXECVE put it in a0), so the image is empty and build_tree skips the node with if not image: continue.

A new reader must set event_type correctly and provide a usable image or name, or the tree silently shows nothing.

Robustness rules: wrap each record in try/except (a bad record is logged and skipped, never fatal); if a third-party library is missing, fail with a clear install message and keep the format disabled in the UI; detect by magic bytes where possible; ship a tiny sample under samples/ with a test asserting the normalized output.

5. Detection modules

Each module exposes a run(events, tree) that returns signals. Sigma matching uses literal substring matching, not regex: write | bash or | sh, not wildcard patterns. The engine is OS-gated: Windows modules run when the host OS is Windows, Linux modules otherwise. Scores combine as max(scores) + 0.05 * (n_sources - 1), capped at 1.0, so corroboration raises confidence rather than averaging it down.

6. SOAR and playbooks

orchestrator._handle matches a signal to a playbook, builds the ticket with Ticket.from_signal, executes the playbook steps, then sets status to open. The TicketStore appends to tickets.jsonl; regenerating sample data requires deleting that file first, or tickets accumulate.

7. The frontend SPA

The whole UI is one HTML string in frontend.py, served at /. It must stay ASCII (a recurring bug reintroduced the box-drawing character U+2500 in comment separators; scrub before shipping). Navigation is tab based: Dashboard, Open, My Tickets, Signals, Run SIEM, Templates. State lives in a few globals; the History API drives back/forward. Tickets and templates persist drafts in localStorage.

Two conventions worth keeping. First, clickable elements use data- attributes plus a single handler (goScope(this)) rather than inline calls with nested quotes, which avoids an escaping nightmare. Second, the modal closes only when a click both starts and ends on the backdrop, tracked with a mousedown flag, so a text selection released outside the note does not close it.

9. Mode seam

SIEM_MODE (env) selects local or server behavior, fixed at launch. The app binds to loopback by default (SIEM_HOST overrides). File analysis (browser, run-on-file, pcap, evtx) is local only and hidden in server mode. The mode must come from a trusted server-side source, never a client input.

10. Tests

Tests are print-based scripts under tests/, run with PYTHONPATH=src python3 tests/test_X.py. Use scripts/run_tests.sh or scripts/run_tests.bat to run all of them with a per-file PASS/FAIL line and a total. Keep the suite green and add a test for every new reader.
